# pinwash architecture

**North star:** on a pair of git trees (`base` / `head`), using a closed surface set and a closed rule-ID set, flag harness weakenings that make an agent more able to claim done. The verdict is replayable: no network, no LLM, no subject execution.

This file explains layers and evolution. It does **not** add rules, surfaces, exit codes, or acceptance criteria.

**Conflict rule:** [SPEC.md](SPEC.md) wins. [THREATMODEL.md](THREATMODEL.md) owns residual rows. Frozen acceptance is [tests/gates/test_v0_acceptance.py](tests/gates/test_v0_acceptance.py). Coding agents have read-only authority over `tests/gates/**`. SPEC rulings and edits are delegated to the maintaining agent (SPEC preamble, 2026-09-27): each one bumps the spec version, lands as its own commit, and re-runs the fixture suite. If this file disagrees with SPEC, SPEC is correct and this file is wrong.

SPEC's opening records the local engine and the 2026-09-27 delegated edit authority. This checkout has a **local v0 engine** at `0.0.0` / spec `16` (each bump is its own commit with a changelog entry in SPEC §16). That is not a Release, not PyPI, and not a 1.0 claim.

## 0. What this product is allowed to be

pinwash is a static, local, deterministic **diff scanner**. It judges **harness weakening**, not product tests, not claims, not journeys, not whether a hook actually ran.

It never emits `SECURE`, `HARNESS_INTACT`, `HONEST`, `COMPLETE`, or `ENFORCED`. The strongest valid pass sentence is SPEC §0:

> No in-scope weakening finding at or above `fail_on` was observed on this base/head pair, under this spec version, surface set, and pinwash revision.

A1–A11 holding does **not** license a public 1.0 (SPEC §12).

## 2. Trust boundaries (invariants)

1. The **head** tree — including the working tree — is attacker-controlled. Agents write it. In hook and worktree mode that includes the repository's own `.git`: its config, refs, hooks, `info/` files and object store.
2. **Configuration and allowlists are read from the base side only.** A head-side disable does not govern the run that reviews that head. Creating a base-absent config that relaxes defaults is itself a finding (`CONFIG_RELAXED`).
3. The core path **reads bytes**. It never executes subject code, hooks, judges, workflows, MCP servers, or skills, nor a program the subject repository's git configuration names. It never uses a network. It never calls a model.
4. GitHub rulesets that exist only on an API and not as a file in the trees are residual R05: `UNKNOWN`, not pass and not block.
5. The analysis unit is a **diff** (`base`/`head`). pinwash never judges a single snapshot as “the harness is fine”.
6. Missing observation is never a pass: unobservable inputs surface as `SURFACE_UNPARSEABLE` findings, `config_errors` entries, or `unknown_coverage` rows. A crashed engine is exit **2**, never a block (exit 1). Subject-surface parse failure is `SURFACE_UNPARSEABLE`, not exit 2, unless git itself cannot be read.
7. Artifacts the agent wrote in the same diff (logs, screenshots, “CI is green” prose) are never evidence that a harness still runs.

**Git hardening (H0, 2026-10-09; engine only, no spec bump).** Items 1 and 3 hold for git itself: every git call runs as `git --no-replace-objects -c core.fsmonitor=false -c core.commitGraph=false -c core.untrackedCache=false -c core.hooksPath=<no file>` (and, since spec 16, `-c core.ignoreCase=false`) with `GIT_NO_LAZY_FETCH=1`, `GIT_ALLOW_PROTOCOL=` (empty), `GIT_GRAFT_FILE` and `GIT_SHALLOW_FILE` naming no file, and stdin from the null device. Command-line `-c` outranks every config file, `include.path` and `includeIf` targets and `config.worktree` included. Every commit, tag, tree and blob read from the object store is rehashed against its id (SHA-1 or SHA-256 by `rev-parse --show-object-format`); a commit's tree id comes from its verified body, never from a commit-graph or a `^{tree}` shortcut; tree listings are parsed from verified tree objects; a mismatch is an unreadable git tree, exit 2, never a pass. `BASE...HEAD`'s merge base is computed from verified commit objects with git's algorithm (`paint_down_to_common` and `remove_redundant`, the same queue order, committer dates read as git's `parse_commit_date` reads them); `git merge-base` is not asked. Commits are read ahead in batches (`git rev-list` from the walk's frontier, piped into one `cat-file --batch --buffer`); that listing is a hint, and only objects that rehash are kept. A missing object is exit 2 that names it. A tree that lists one name twice or breaks git's entry order (git fsck's duplicateEntries / treeNotSorted) is malformed, exit 2: git itself reads it two ways (ls-tree -r lists both entries, diff-tree takes the first), and reading the last one let a committed Stop removal pass `BASE..HEAD` (second H0 review). The work tree must be the directory holding the `.git` that git found, or, with `GIT_DIR` set, the cwd (git's default there), unless the judge sets `GIT_WORK_TREE`. ```mermaid

  participant Engine

  CLI->>Git: trees for base and head

- `pinwash check` with no range: `HEAD` versus worktree. Worktree is the attack surface (tracked and untracked, `--exclude-standard`).
- Default `fail_on` is `high`. `warn` does not fail the run (A6: phrase hit on skill markdown is warn, exit 0). `PERMISSION_WIDENED` and `CONFIG_RELAXED` escalate to **high** (`CONFIG_RELAXED` at `.pinwash/allow.toml` is **critical**, SPEC §10); `EXEMPTION_ADDED` is **critical** when an added record's `created` is after today (spec 11). Last remaining Stop-like hook, last remaining required context, or last non-floating pin on a workflow (when floated) escalate per SPEC §6.
- stdout JSON is the **only machine API**: UTF-8, sorted keys, `ensure_ascii=False`, newline `\n`. Human reports may degrade glyphs; machine JSON may not. A lone surrogate in a value (a non-UTF-8 path name decoded with `surrogateescape`, a JSON `\udXXX` escape) is written as a `\udXXX` escape inside its string, which loads back to the same value, and is fingerprinted through `surrogatepass`; every other string encodes and hashes as before (0ddcd57). It used to crash to exit 2.
- `unknown_coverage` does not change `verdict`, and a row never adds, drops or changes a finding. Its `reason` is fixed text from the closed list in SPEC §7 (spec 13; spec 14 added the workflow rows): the §3.1 grammar hits, the hook-side rows of SPEC §3.3 and §5.1, and the required-check producer rows of SPEC §5.5. A consumer that requires “no unknown coverage” is **consumer policy**, not this spec.
- `pinwash_findings_version` is `1`. `spec_version` tracks SPEC §16 (currently `16`). `pinwash_version` is `0.0.0`.

JSON surfaces parse the same at any nesting depth and any integer length (0ddcd57). Every document the engine judged before is judged the same, and the ones it crashed on are judged on all three interpreters. A JSON surface is `unparseable` only for a syntax error or bytes that are not UTF-8. ### 5.1 Bounded GHA grammar (v0)

After CRLF→LF: drop comment lines; spaces-only indent (SPEC §3.1 states the tab rule since spec 12: a tab before a line's first `#`, or anywhere on a line without one, fails the whole file); record `uses:`, `continue-on-error:`, `if:`, job keys (exactly two spaces under `jobs:`), and job `name:` under the stack in SPEC §3.1, plus (spec 8) the triggers of a column-0 `on:`: inline scalar, inline `[a, b]`, and indent-2 block list items or mapping keys. Every recorded value is truncated at the first ` #` (spec 5). Spec 14 records, as text the SPEC §5.5 rows compare and never evaluate, the configuration lines of `push` / `pull_request`, and at job indent `needs:`, `strategy:`, a job-level `uses:`, a multiline job `if:` as its lines, and the step run keys (`if`, `continue-on-error`, `shell` inside the job's `steps:` / `defaults:` blocks and the workflow's column-0 `defaults:`, a `- ` item at job indent included, never under a step's `with:` or `env:` or inside a script body; each with its step's identity, and flow-style values as text); a column-0 line ends the job table. Since the spec 14 reviews the job-table grammar rows are reported only while a base ruleset names a context, for a changed file or a partly read job table while another callable workflow changes; `workflow layout unresolved` reports document forms the grammar does not read (a byte order mark, NEL / LS / PS line breaks, an indented document, a second document, and keys behind a tag, anchor or `?`); quoted scalars left open on their line, and flow values left open, run to their close as text; job keys and `jobs:` with an inline comment are read; steps sharing an identity are told apart by their order.

Residuals, not findings, not passes: YAML aliases, multiline scalars, `uses` split across lines, `true` written as `yes`, jobs generated by reusable workflows, `workflow_call` indirection, and an `on:` block the grammar cannot resolve (spec 8). Those are `unknown_coverage`, reported from either side once per (path, reason). #4 (c11e958) routed values outside the closed forms there without a bump: a block-scalar header or empty remainder on `uses`, `continue-on-error`, `if` or job `name`; `continue-on-error` other than `true` / `false`; a block-scalar `on:`. #4 left a step-level `continue-on-error:` silent where the same forms of step `if:` gave the row; the commit before spec 14 gives it the row too, `- ` first and at any indent (#14, no bump, AI-assisted ruling R-14). `docker://` uses has been unknown since spec 0. A quoted `"on":` / `'on':` key is an unresolved `on:` block whose triggers are not read (8af4d6f). A head `on:` block unresolved wholly or in part is never an observed trigger removal; at base only the triggers the grammar resolved count, because an unresolved base item can only add triggers (a quoted base key resolves none). At head this routes two trigger losses that `c71c468` blocked to an `unknown_coverage` row alone: a quoted `"on":` key, and an indentless flow-map item such as `  - {cron: …}` under `schedule:` beside resolved triggers. `on: {workflow_dispatch: {}}` already took that route; reading these forms widens the grammar (§10). The engine must not invent “no `uses` change” from an unparsed construct.

Outside the grammar, booked as SPEC §11 R20 in spec 12 and routed in spec 14 (AI-assisted rulings on #23 and #24): quoted keys other than `on` (`"jobs":`, `"uses":`) and `key :` spacing (`quoted or spaced key unresolved`), flow-style job bodies (`flow-style job unresolved`) and JSON-syntax or other flow-style workflows (`flow-style workflow unresolved`) (#23), job keys not at indent 2 or job bodies not at indent 4 (`jobs indentation unresolved`), and a top-level key after `jobs:` (`top-level key after jobs unresolved`; the key now ends the job table, so its children are no longer phantom jobs) (#24). These rows come from either side; since the spec 14 reviews the job-table rows are reported only while a base ruleset names a context, for a changed file or a partly read job table while another callable workflow changes, so a repository that keeps such a form does not see them on every scan. A job the grammar cannot resolve is unresolved, never an observed deletion: a requoted, spaced, flow-style or reindented table, or a job whose own key is requoted, spaced or flow-style, no longer reads as `deleted` (the trade, both ways, is in SPEC §16 row 14), while the workflow's triggers are still compared; a job key spelled so hides no other job's deletion (`GhaFile.unresolved_job_keys`). Still read wrongly, not ruled: a requoted `uses:` reads as a removed pin. A job key or `jobs:` followed by an inline comment is read as its key since the spec 14 review (before, it matched neither form and the lines under a commented job key were read as the job before it; §9 item 9). R20 also books the tab rule's costs: honest tabs that block, and an unparseable base that leaves later weakenings in that file at one warn, or at nothing when the same edit removes the tab (R19) (#25).

### 5.2 Pin identity

A pin is `{locator, kind, value, product?}` as in SPEC §4. Locator examples must stay stable across reformatting.

Kind lattice, stronger to weaker:

```
digest_sha256 > git_sha (full 40 hex) > git_tag > action_ref-that-is-tag > floating
```

`JUDGE_UNPINNED` is kind moved down the lattice; value changed to floating; pin removed while the consumer still exists; digest present at base and absent at head; SHA shortened below 40 hex.

Tightening (tag → sha, sha + digest added) is not a finding. Vendor-directory **content** edits without a pin-record change are residual R04 in v0.

`.pinwash/pins.json` is optional. Head-only creation is not a finding. If present at base, every record must keep kind/value or a documented allow fingerprint (SPEC §4, §10): an unpin event is high, and since spec 15 any other kind or value change that is not tightening is a `warn` row (`declared pin <locator> value changed`); a `digest_sha256` value is non-floating only as `sha256:` and 64 lowercase hex.

Fingerprint (exemption key): `rule/path/v1:` plus hex sha256 of canonical JSON `{rule, path, locator, before_digest, after_digest}`. Allow entries are per fingerprint, never per-rule-glob; all six keys required; `expires` at most 180 days after `created` and not before today to be valid (visible to the add/edit/delete checks), and at most 180 days after the earlier of `created` and today to be in force, with no other valid record for the same fingerprint and rule whose `created` is after today (spec 11). Allow-channel findings at `.pinwash/allow.toml` are never exempted (spec 11).

## 6. Exit codes and determinism

| Exit | Meaning |
|---|---|
| 0 | No finding at or above `fail_on`; engine finished |
| 1 | Verdict `block` |
| 2 | Engine error, including unexpected exceptions and unreadable git trees |

No floats in the verdict path. No network. No clock in findings JSON (exemption date is the exception above). No random. Zero runtime dependencies. SPEC §9 requires JSON bytes identical on Windows / macOS / Linux for the same trees and Python 3.11–3.13. A10 checks less: LF versus CRLF subject files, one interpreter, one host. A local Linux run on `f849b8a` compared stdout bytes and exit codes across CPython 3.11, 3.12 and 3.13 with two hash seeds (README status row). Not CI-verified; Windows and macOS untested. Subject bytes no longer pick an interpreter- or host-dependent path: a deep JSON document is read iteratively and judged on all three, where 3.11 exited 2 and 3.12/3.13 judged it, and `PYTHONINTMAXSTRDIGITS` no longer moves a long integer between judged and exit 2 (0ddcd57).

## 7. Consumers (outside the core)

pinwash may be **wrapped** by a hook or a CI job. It remains not an enforcer. Job failure on exit 1 is **repository policy**.

| Consumer | How | What it is not |
|---|---|---|
| Local / pre-commit | `python -m pinwash check` or `HEAD~1..HEAD` | Proof the remaining harness works |
| PR CI | Runner already has two trees; run `BASE...HEAD` | pinwash executing a GitHub required check |
| Stop hook runner | May shell out to pinwash | Closing residual R01 (a host CLI that never consults repo hooks) |

Forbidden consumer fantasies:

- Call a GitHub ruleset API to close R05.
- Call a model to close R08.
- Auto-fix the diff (another product).
- Treat `unknown_coverage` as pass.

`doctor` (SPEC §13): own tests **and** spec hash; must not judge the subject (`subject_judged: false`). It runs this package's unittest suite in-process under a `PINWASH_DOCTOR_SELFTEST` guard (the gate suite spawns `pinwash doctor`, so the guard stops a doctor running inside its own test run from recursing); own-test failure is exit 2.
