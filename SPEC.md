# pinwash SPEC — frozen contracts

**One sentence:** pinwash flags a Git diff that makes an agent more able to claim done by weakening the verification harness around it.

**一句話：** 標出會讓 agent 比較容易自稱完成的 harness 變更。

This file is the single source of truth for rule IDs, pin identity, surfaces, severity, exit codes, and determinism. Changing anything here requires a spec-version bump and a fixture re-run. Authority: the human maintainer owns `tests/gates/**`; on 2026-09-27 the maintainer delegated spec rulings and edits to the maintaining agent, under the discipline that every change bumps the spec version, lands as its own commit, and re-runs the fixture suite. On 2026-10-09 the maintainer extended that delegation to every ruling, including one that reverses SPEC text or turns a passing result into a block, on the condition that each ruling the maintaining agent makes is marked **AI-assisted** in its §16 row, its commit message and its issue; rulings the maintainer makes are marked as the maintainer's.

Spec version: **29** (draft spec 0 was frozen by the first commit of this file; the findings envelope is `pinwash_findings_version: 1`). A local engine exists (`pinwash` 0.0.0, stdlib only, zero runtime dependencies); it is not a Release, not on PyPI, and not a 1.0 claim. This document began as the preregistration: acceptance in §12 was frozen before implementation. Detectors must not be patched to fit a fixture; fixtures that are out of spec stay residuals.

## 0. What it is / is not

| It is | It is not |
|---|---|
| A static, local, deterministic **diff scanner** | An enforcer, hook, or required status check |
| A judge of **harness weakening** | A judge of product tests, claims, or journeys |
| Fail-closed on its own parse errors | Proof that the remaining harness works |

It **never** emits `SECURE`, `HARNESS_INTACT`, `HONEST`, `COMPLETE`, or `ENFORCED`. The strongest valid pass sentence is:

> No in-scope weakening finding at or above `fail_on` was observed on this base/head pair, under this spec version, surface set, and pinwash revision.

A pass is not enforcement. tripwire (or GitHub rulesets) may still be absent, skipped by a human `--no-verify`, or running a different pin. pinwash does not install, invoke, or trust those tools.

### Neighbours (do not reimplement)

| Product | Question pinwash does **not** answer |
|---|---|
| checkwash | Did this diff weaken **product tests / CI oracles**? |
| walkaround / action-receipt / claim-receipt-lab | Did the agent **enter** a contract or **emit** a receipt for a done-claim? |
| phaseledger | Did a **measurer** allow a phase advance? |
| charterlock | Was the journey **allowed to be the exam**? |
| tripwire | Is a hook **actually executing** a pinned judge on this host? |
| boundkit | Was the **task** claimed and authorized? |
| smallestlie | What lie does **this** verifier still accept? |

checkwash already rates many guardrail-path edits `GUARDRAIL_TOUCHED`. That event is “a constraint file changed”. pinwash events are **structured weakenings** (hook gone, pin floated, permission widened). Both may fire on one diff. Identities must not be shared.

## 1. Trust model

1. The **head** tree — including the whole working tree in hook mode — is attacker-controlled data. Agents write it.
2. pinwash **configuration and allowlists are read from the base** side only. A head-side config that disables rules does not govern the run that reviews that head. Creating a base-absent config that relaxes defaults is itself a finding (`CONFIG_RELAXED`).
3. pinwash **never executes** subject code, hooks, judges, workflows, MCP servers, or skills. It reads bytes.
4. pinwash **never uses a network** on the core path. GitHub rulesets that exist only on the API and not as a file in the trees are `UNKNOWN`, not pass and not block.
5. pinwash **never calls a model**.
6. Missing observation is never a pass: an input this spec version cannot observe surfaces as a finding (`SURFACE_UNPARSEABLE`), a `config_errors` entry, or an `unknown_coverage` row — never as a silent `verdict: pass`. A crashed engine is exit 2, never a block (exit 1).
7. Artifacts the agent wrote in the same diff (`*.log`, screenshots, “CI is green” markdown) are never evidence that a harness still runs.

## 2. Analysis unit

pinwash analyses a **diff**: a pair of git trees `base` and `head`. It never judges a single snapshot as “the harness is fine”.

Range notation matches checkwash:

- `BASE..HEAD` — tree to tree.
- `BASE...HEAD` — `merge-base(BASE, HEAD)..HEAD`. It must not silently become two-dot.
- `BASE..WORKTREE` (spec 16, AI-assisted ruling on #17) — tree `BASE` to the working tree; configuration, allowlists and every base-side reading (required contexts, hook bodies) come from `BASE`, while the head-side counts §6 escalates on come from the working tree, (§1.2), whose objects are read with replace refs ignored and rehashed (a mismatch exits 2). `WORKTREE` is a pinwash extension of checkwash's notation and a reserved token: it names the working tree only on the right of `..`. A range with `WORKTREE` on the left of `..`, or on either side of `...`, is invalid (exit 2), because the working tree is head-side data (§1.1) and never a base. Any ref git resolves by the name `WORKTREE` (a branch, a tag, a remote's `refs/remotes/WORKTREE/HEAD`, a `$GIT_DIR/WORKTREE` file) is spelled in full, such as `refs/heads/WORKTREE`. The working tree is every file git tracks, read from disk (a tracked file missing from disk is absent), plus every untracked file no ignore rule matches; an untracked file an ignore rule matches is not read (residual R21). Each such file at a fixed-prefix §3 surface path (an exact surface path, or a path under one of the surface directory prefixes `.agents/skills/`, `.claude/hooks/`, `.cursor/rules/`, `.cursor/skills/`, `.github/rulesets/` and `.github/workflows/`), whatever the ignore source, is listed in `unknown_coverage` with reason `untracked surface file matched by an ignore rule, not read`; a `SKILL.md` under no such prefix (the root `SKILL.md` aside, which is listed), and a §3.3 hook-command target outside them, is not listed. The listing reads names only, from literal git pathspecs, so git walks an ignored tree only under a surface directory prefix (an ignored `node_modules` under `.claude/hooks/` is walked, one at the root is not), and a directory directly below a prefix that holds more than one ignored entry is listed once in their place, with reason `untracked surface files under this directory matched by an ignore rule, not read`. An untracked entry git does not descend, ignored or not, is listed with reason `untracked surface directory git does not descend (nested repository or symlink), not read` when it is a nested repository or a symlink at a fixed surface directory (a directory a fixed-prefix surface path sits in or under, such as `.cursor`, `.gemini` or `.claude/hooks`), or a nested repository or a symlink to a directory below a surface directory prefix (`.agents/skills/<name>`); a symlink to a file is read through it, and a tracked gitlink or symlink is not listed (residual R23). Both rows are visibility only (§7). `check` with no range is `HEAD..WORKTREE`.

Paths are normalized to forward slashes. Comparison text is CRLF→LF before parse.

If it was also unparseable at base, emit `SURFACE_UNPARSEABLE` at warn (no new information). The engine emits `SURFACE_UNPARSEABLE` for no other parse-status pair. Since spec 16 (AI-assisted ruling on #22) the other pairs with an unparseable side are `unknown_coverage` rows on every surface, never findings: (missing, unparseable) is `new surface file unparseable`, and its head is not compared; (unparseable, ok) and (unparseable, missing) are `surface unparseable at base`, and the comparison goes on as before (the base is not read: residual R19). The row stays, and every other surface keeps the comparison above. Claude Code reads a settings file whose text trims to empty (no bytes, whitespace, a lone byte order mark) as `{}`; pinwash keeps calling it unparseable, so emptying a settings file blocks (`SURFACE_UNPARSEABLE` high) where the host sees no settings, a conservative reading. A file both sides parse that the host still loads otherwise or not at all is R24. Since spec 19 none of these pairs applies to `checkwash_config`: §3.2 reads it as checkwash does, a text checkwash cannot parse being the defaults, so it is never unparseable.

### 3.1 Bounded line grammar (GitHub Actions YAML)

v0 does not ship a YAML parser. On each workflow file, after CRLF→LF:

- Drop lines whose first non-space is `#`.
- Drop a leading byte order mark (U+FEFF), and read NEL (U+0085), LS (U+2028) and PS (U+2029) as line breaks, as YAML 1.1 parsers do (PyYAML, libyaml, and the YamlDotNet the Actions runner uses; GitHub's own workflow parser is not public, INFERRED); either is reported (`workflow layout unresolved`, below). Before the first content line, `%` directive lines and a `---` document start marker with nothing or a comment after it are not content (spec 14 review).
- A quoted scalar that a key's value or a `- ` item opens and does not close on its line runs to the quote that closes it (a backslash escapes in double quotes, `''` is a quote in single quotes): its later lines are its text, never keys or comments. A recorded key (`uses`, `if`, `continue-on-error`, `shell`, a job `name:`) whose value spans lines so is `multiline uses or scalar`; a job `if:` compares as its lines (§5.5), a step run key takes them as its text, and such a `uses:` value is not read as a pin. A quote inside a block scalar's body opens nothing. Likewise a flow collection (`{…}` or `[…]`) that a key's value or a `- ` item opens and leaves open on its line runs, at any indent, to the bracket that closes it (brackets inside quotes and after a comment not counted): its later lines are its text, never keys; a `needs:`, `strategy:` or trigger configuration value so written takes them as its text, and an `on:` list so written is `on triggers unresolved` (spec 14 review).
- Track indentation width in spaces. **Tab rule** (stated in spec 12; the engine has applied it since spec 0): a line that contains a tab (U+0009, written `<TAB>` here) before its first `#` character, or anywhere when the line has no `#`, makes the whole file unparseable under §3, and none of its pins, jobs or triggers is compared. The test runs on every line, split at LF, CRLF, a lone CR or (since the spec 14 review) NEL, LS or PS, before comment lines are dropped, and the first `#` counts wherever it stands (in a value, inside quotes, with or without a space before it). So a tab in indentation, in a value or in block-scalar content, before an inline comment (`if: false<TAB># x`), on a whitespace-only line, or before the `#` of an indented comment line fails the file; a tab after a line's first `#` does not. The rule is not narrowed to indentation: recorded values truncate only at ` #` (below), so `if: false<TAB># x` would then stop reading as `false` (#25). Its costs are residual R20.
- Record:
  - `uses:` value (strip quotes) at any indent.
  - `continue-on-error:` value `true` / `false` at job indent (the §5 disjunct). The same key deeper than job indent, or after a `- `, is a step run key (below).
  - `if:` value as raw remainder of the line. A plain value continued on deeper lines, one value YAML folds, is multiline like a block scalar: recorded as its first line and its later lines, and reported as `multiline uses or scalar` (spec 22 review).
  - `name:` at job indent (the first `name:` under a `jobs:` key at indent 2, using a stack). A double-quoted value holding a `\` is an escape the grammar does not decode: that job's context is unresolved (spec 14 review). A plain value continued on deeper lines, one value YAML folds, is multiline: the context is unresolved and reported as `multiline uses or scalar` (spec 23 review). The value as written, quotes and any anchor kept, is recorded for §5's reading of a name (spec 23).
  - Job keys: a line matching `^  [A-Za-z0-9_-]+:` under `jobs:`, followed by nothing or by spaces and an inline comment (the comment form since the spec 14 review, as for `jobs:` itself). A later column-0 line ends the job table (spec 14).
  - `on:` triggers (spec 8), at column 0 only: inline scalar, inline `[a, b]` list, block list items (`- item`) at indent 2, block mapping keys (`key:`) at indent 2. Deeper lines under a trigger are trigger configuration, not triggers. A second top-level key ends the `on:` block.
  - Spec 14, recorded as text for the §5.5 rows and never evaluated: the configuration of the `push` and `pull_request` triggers (the remainder after `push:` on its line, then every deeper line under it, in order); and, at job indent (4) under a job key, `needs:` and `strategy:` (the remainder on the key's line, then each deeper line, or `- ` item at job indent, below it), a job-level `uses:` (a reusable-workflow call), a job-level `if:` whose value is a block scalar or empty, as its header and deeper lines (no §5 reading), and the *step run keys*: a line inside the job's `steps:` or `defaults:` block, or inside a column-0 `defaults:` block (the workflow's), whose key, after an optional `- `, is `if`, `continue-on-error` or `shell`, deeper than job indent or a `- ` item at job indent, and not deeper than a step's `with:` or `env:` key or than a key whose value is a block scalar (a script body). A step run key whose value is a block scalar or empty takes its deeper lines as its text. A flow-style value or item in those blocks (`- {run: …, if: …}`, `defaults: {run: {shell: …}}`, `steps: [ … ]`) is recorded as its text, with the following lines while its brackets stay open. Each is recorded with the step it belongs to (spec 14 review): a `- ` item at the indent of the block's first item starts a step, identified by its `id`, else its `name`, else its `uses` value without the part from its last `@`, else its `run` text (a block-scalar `run:` by the first line of its body), else its position in the block; steps that share an identity are told apart by their order; a `defaults:` block is one step.

Every recorded value is **truncated at the first ` #`** (space followed by `#`) — the bounded form of a YAML inline comment. A `#` without a preceding space is kept. Spec 5 added this truncation after live-fire on a real repository showed sha-pinned `uses:` lines annotated `# vX.Y.Z` classified as floating, so honest release annotation bumps fired `JUDGE_UNPINNED`. Residual: a quoted value that legitimately contains ` #` truncates at the wrong point.

**Residuals (not findings, not passes):** YAML aliases (`*anchor`), multiline `>` / `|` scalars, `uses` split across lines, `true` written as `yes`, jobs generated by reusable workflows, `workflow_call` indirection, and an `on:` block whose forms the grammar cannot resolve (flow mapping `on: {…}`, unrecognized items, a quoted `"on"` / `'on'` key or `on :` → recorded as unknown `on triggers unresolved`, never treated as an observed trigger removal). Those are `UNKNOWN` coverage, documented in THREATMODEL, never invented as “no `uses` change”. A multiline scalar is one at any indent: a step-level `continue-on-error:` block scalar or empty value is `multiline uses or scalar`, as the same forms of step `if:` are (the engine commit right before spec 14, #14). Jobs generated by reusable workflows and `workflow_call` indirection report `reusable workflow producer unresolved` when they produce a required check and the diff touches that job or what it calls (§5.5, spec 14).

**Outside the grammar, reported** (residual R20, booked in spec 12; routed in spec 14, AI-assisted rulings on #23 and #24). Each form below is read as nothing and reported on either side, once per (path, reason):

- `quoted or spaced key unresolved`: a line whose key, once one pair of matching quotes around it and any spaces before its colon are removed, is a key this grammar records where it records it (`uses`, `if` or `continue-on-error` at any indent, after an optional `- `; `name`, `needs`, `strategy`, `steps` or `defaults` at job indent under a job key; `shell` inside a job's `steps:` or `defaults:` block or the workflow's `defaults:`; `jobs` or `defaults` at column 0; a job key under `jobs:`), while it is not in the bare `key:` form. The quoted or spaced `on` key is `on triggers unresolved` (above).
- `flow-style job unresolved`: a job key under `jobs:` with a value after its colon on the same line (`  ci: {…}`; an inline comment alone is no value), or `jobs:` with one.
- `flow-style workflow unresolved`: a file whose first content line (after any `%` directive lines and a `---` marker, or on the marker's line after `--- `) starts with `{` or `[` (JSON syntax included). Nothing else in it is read (the tab rule still applies), and its `on:` is unresolved.
- `jobs indentation unresolved`: the first line under `jobs:` that is not a comment is not at indent 2 (no job of that table is read), or a job's first body line is not at indent 4 (nothing in that body is read; its key is).
- `top-level key after jobs unresolved`: a line of the job-key form at indent 2 under a column-0 key other than `on:` that follows `jobs:`. That column-0 key ends the job table, so the line is not read as a job, as it was before spec 14 (#24).
- `workflow layout unresolved` (spec 14 review): a leading byte order mark (the file is read past it) or a NEL, LS or PS line break (read as one); a first content line not at column 0 (a document indented as a whole), or content other than a flow collection or a comment on the `---` marker's line; after the first content line, a column-0 line that starts with `?`, `!`, `&`, `*` or `%` (an explicit key, a tag, an anchor or alias, a directive), or a second document (a `---` marker, or content after a `...` end marker), of which nothing is read; and, at any indent after an optional `- `, a key behind a tag or an anchor (`!!str if: false`, `&a if: false`) or an explicit `? key`, which is not read. Where such a form stands at column 0, a missing job is then unresolved, not deleted, and an `on:` block that resolves no trigger is unresolved; resolved triggers are still compared. A `...` marker that ends the file is not this row, and neither is a column-0 `- ` item (a compact sequence under a key) or a plain scalar's continuation line that starts with `!`.

The job-table forms (`jobs indentation unresolved`, `flow-style job unresolved`, `top-level key after jobs unresolved`, `quoted or spaced key unresolved` for any key but `uses`, and `workflow layout unresolved` for a key form inside `jobs:`) are reported only while a base `gha_ruleset` file names a context, for a file the diff changes (its text after CRLF→LF differs between the sides), or for a file whose job table is read only in part (a job table, job key or job body in a form above, a job-level key spelled or written behind a tag, anchor or `?`, or a flow-style workflow) while the diff changes another workflow file whose `on:` names `workflow_call` on either side, which a job it does not read may call: only §5 reads the job table, and it reads nothing without such a context (spec 14 review). The other rows here are reported on every scan, as the other §3.1 grammar hits are.

A job the grammar cannot resolve is unresolved, never an observed deletion, as an `on:` block is: a base job missing at head is not `deleted` (§5) when the head's job table is unresolved as a whole (a quoted, spaced or flow-style `jobs` key, a flow-style workflow, job keys at another indent) or when the head spells that job's own key outside the job-key form (quoted, spaced, or with a value on its line), and its workflow's triggers are still compared. A job key spelled so leaves only that job unresolved: it does not hide the deletion of another job. A key in these forms is not read, so a requoted `uses:` still reads as a removed pin (§4; not ruled in spec 14). A job key or `jobs:` followed by an inline comment (`  ci: # main`) is read as its key since the spec 14 review; before, it was read as neither, the lines under such a job key as the job before it, and an honest comment added to a producer's key fired `deleted` high.

### 3.2 checkwash config, read as checkwash reads it

Since spec 19 (AI-assisted ruling R-22b on #22, with the challenger's amendments) `checkwash_config` is read the way checkwash reads it (its `config.load_config` and `read_base_config_file`). Per side, the config in force is the first of `.checkwash/config.toml`, `.greenwash/config.toml` that exists as a file at that exact path, as checkwash's `git show REV:<path>` reads it (no other spelling, such as a root file named `.checkwash\config.toml`, is a config; a tree or gitlink at the path is R22; in worktree mode a symlink at the path is read as its link text, as git will store it); an empty file exists, and a side with neither runs on the defaults (`fail_on` `high`, no detector disabled). Its bytes are decoded as UTF-8 with a leading byte order mark dropped and bad bytes replaced by U+FFFD, then parsed with Python's `tomllib` (TOML 1.0); a text `tomllib` rejects is the defaults. pinwash reads only `gate.fail_on` (exactly `info`, `warn`, `high` or `critical`; any other string, number, date or boolean is the default) and `detectors.disable` (a list of strings; any other value disables nothing). checkwash also reads `roles` and `gate.on_engine_error` (R22) and ignores every other key, a top-level `fail_on` included. A `checkwash_config` file therefore has no parse status (§3). A config checkwash cannot load, on which it exits 2 instead of running, is reported as the `unknown_coverage` row `checkwash config checkwash cannot load (not compared)` (§7): one whose `gate.fail_on` is an array or a table (checkwash's `in` test raises), one with a decimal integer of more than 4300 digits (Python's default limit, which pinwash applies whatever the environment says), and one in which `tomllib` meets, before any error it reports, an array or inline table nested past 500 levels or a key of more than 1000 parts. At head such a config is not compared; at base the head is compared against the defaults, as if it created its config. The bounds are fixed so that the reading is the same on every interpreter and call stack: checkwash runs `tomllib` under Python's default recursion limit of 1000 frames, and every level costs `tomllib` at least two, so no config nested past 500 levels loads in checkwash (one nested between about 330 and 500 levels may already fail there, depending on how checkwash is launched, and pinwash compares it); 3.11's and 3.13's `tomllib` refuse a key of more than 1000 parts, and 3.12.3's does not. Through spec 18 this section was a bounded single-line subset that read `fail_on` lines under any table and `detect_* = false` assignments.

### 3.3 Hook command target resolution

A hook `command` string (from `claude_settings` or `cursor_hooks` JSON, on a given side) resolves to target files as follows, and nothing else: on `claude_settings`, rewrite the project-root forms below (spec 26); strip surrounding quotes; replace `;`, `&`, and `|` with spaces; split on whitespace. A token is a target iff it fully matches `[A-Za-z0-9_./-]+\.(py|sh|bash|js|mjs|cjs|ps1)`, does not start with `/`, `-`, or `~`, and names a path present in that side's tree after path normalization. Resolved targets are `claude_hooks` surface members for the §3 parse-status check and the §5.2 body check, in addition to `.claude/hooks/**` paths.

**Project-root forms (spec 26, AI-assisted ruling R-18a(c), hook-project-dir, #18).** Claude Code runs a hook with `CLAUDE_PROJECT_DIR` set to the project root whose settings files it reads (the directory it was launched in, or the one Claude Code 2.1.296's `--project-config-root` names), which is the repository root whenever it reads the repo-root settings files (launched in a subdirectory, it does not run their hooks), and it sets that variable after the settings `env` and the launching environment, so neither redirects it (each EXECUTED on Claude Code 2.1.42 and 2.1.296). A `claude_settings` command, spaces, tabs and line feeds at either end trimmed, is first read as words split at spaces and tabs, from its start. A *root word* is `"$CLAUDE_PROJECT_DIR"/P`, `"${CLAUDE_PROJECT_DIR}"/P`, `$CLAUDE_PROJECT_DIR/P`, `${CLAUDE_PROJECT_DIR}/P`, `"$CLAUDE_PROJECT_DIR/P"` or `"${CLAUDE_PROJECT_DIR}/P"`, where `P` is one or more of the characters `A`–`Z`, `a`–`z`, `0`–`9`, `_`, `.`, `/` and `-` and does not start with `/`, optionally followed in the same word by text that starts with `;`, `&`, `|`, `<` or `>`; it is rewritten to `P` and that text. A *plain word* is printable ASCII (`!` to `~`) and holds none of `$`, backquote, `"`, `'`, `\`, `;`, `&`, `|`, `(`, `)`, `<`, `>`, `{`, `}` and `#`; a character the shell keeps in a word, such as CR or a no-break space, ends the reading (the host runs another file or none there, executed). The reading goes on over plain words and root words, and stops at the first other word or after a root word that such text follows; the rest of the command is kept as written, and the steps above run on the result. So `bash "$CLAUDE_PROJECT_DIR"/.claude/hooks/stop.sh` and `"$CLAUDE_PROJECT_DIR/.claude/hooks/stop.sh" --hook` resolve `.claude/hooks/stop.sh`. A prefix assignment is a plain word: `CLAUDE_PROJECT_DIR=x "$CLAUDE_PROJECT_DIR"/…` runs the project copy (EXECUTED). A plain word before a root word can still change what runs, as it can before a plain target: an interpreter, `PATH=…` or `BASH_ENV=…` before `bash "$CLAUDE_PROJECT_DIR"/…` runs a repository file first or instead, and a glob or `~` word expands (EXECUTED; R07). The unquoted `$CLAUDE_PROJECT_DIR/…` and `${CLAUDE_PROJECT_DIR}/…` run the project copy only while the project root's path holds no space, tab or glob character: with a space or tab the host splits the expansion and runs no project file, and with a glob character it runs the first path the word matches, which can lie outside the repository (EXECUTED; R07). Not read, because the shell runs another file there or a command can reassign the variable before it (each EXECUTED on both hosts): a form after `;`, `&&`, `||`, `|` or a line break (`X=…;`, `export`, `for`, a sourced file), after any other word (one outside the plain set, which can parameter-expand, quote or run something: `$((CLAUDE_PROJECT_DIR=0))`), and a form single-quoted, escaped or written for another shell (`'$CLAUDE_PROJECT_DIR'/…`, `\$CLAUDE_PROJECT_DIR/…` and, on a POSIX shell, `%CLAUDE_PROJECT_DIR%/…` run a directory literally so named; `$env:CLAUDE_PROJECT_DIR` is PowerShell's, INFERRED from the 2.1.296 source). Not read either, though the host runs the project copy (EXECUTED), so that the list stays closed: `${CLAUDE_PROJECT_DIR:-.}/` and other defaults, `//` after the variable, and a `..` segment, which a symbolic link can redirect. The forms are not read on `cursor_hooks`, nor for a command string that, on that side, only hook objects holding `args` or a `shell` other than `"bash"` hold (any object §5.1 reads a `command` from, in any `claude_settings` file): Claude Code 2.1.296 runs `args` as an exec form, where `$CLAUDE_PROJECT_DIR/…` names a directory literally so named, and `shell: "powershell"` runs no file there (EXECUTED); 2.1.42 ignores both keys. A string that any other hook object holds is read: an added object that holds a judge's string with `args` or such a `shell` (at the matcher-group level, which neither host runs, under another event, or in `settings.local.json`) changes nothing the host runs for the judge (EXECUTED), so it does not turn the forms off for it.

Residuals: module-form commands (`python -m pkg.mod`), quoted paths containing spaces, tokens with variable expansion (`$HOME/...`) other than the project-root forms, inline `-c` payloads, and targets absent from the tree. Targets outside the extension set (other extensions, case variants such as `.PY`, no extension, suffixes such as `.bak`) and a path quoted as a whole token (`python "hooks/judge.py"`: quotes are stripped only from the ends of the whole command) do not resolve either. All of these are residual R07 (#18). A retarget from a resolved judge into one of them is R12 (#10); shell composition around a command that still resolves is R11 (#9). None of these are invented as stubs, and no body check reads the files behind them. For the §6.1 count an unresolved command is live under the same test as any other command (§5.2), because no body is read for it; its string and skip flags are tested as for any command (spec 13, AI-assisted ruling on the tension R12 recorded, #10). Since spec 27 one the diff added to a Stop-like event does not keep the escalator off, because §6.1 counts an added command only when it resolves to a target that can refuse (R12, AI-assisted).

**Unknown coverage (spec 13).** Four reasons route what this resolution leaves unread to `unknown_coverage` (§1.6, §7), each reported at most once per hook surface file. A command is *active* when it carries no §5.1 skip flag (its own or an enclosing object's), is not a §5.2 stub string and does not begin with `#`.

- `hook stop liveness rests on an unresolved command`: a Stop-like hook finding in the file (§6.1) is kept below critical only because an unresolved command counts live (since spec 27 one that was in its event at base); or the diff leaves the file's Stop liveness resting only on unresolved commands (at head a Stop-like event keeps a command live under §5.2 and no such command of a Stop-like event resolves, while at base one did).
- `hook command target no longer resolved`: in an event present on both sides, an active command that resolved at base is active at head with the same string and resolves to nothing there; or an active command that resolved at base is absent from the head event while a command active at head and not active in the base event (absent from it, or flagged, stubbed or commented out there) resolves to nothing at head. No row for a command dropped with no replacement, for a replacement that resolves, or for a removed event (`HOOK_REMOVED`'s case).
- `hook command names a changed file it does not resolve`: an active command, on either side, names a path whose bytes differ between base and head (added, edited or deleted; compared after CRLF→LF, §2, a lone CR kept, so rewriting a shell judge's line feeds to lone CRs is a change) and that is not one of that command's own targets on that side. Reading `\` as `/`, a command names a path when the path occurs in it with the start of the command, whitespace, or one of `" ' / = ; & | (` and backquote before it, and the end of the command, whitespace, or one of `" ' ; & | ) < >` and backquote after it. A `-m` token followed by a token that is an ASCII dotted identifier (`a.b`: one or more dot-separated runs of ASCII letters, digits and `_`, none starting with a digit) also names `a/b.py`, `a/b/__init__.py` and `a/b/__main__.py`. Since spec 26 the project-root forms resolve, so an honest edit of a script behind one gets no row; behind a spelling §3.3 still does not read (`${CLAUDE_PROJECT_DIR:-.}/…`, a form after an operator) it does, and the row says that the edited body was not judged, not that the edit is suspect.
- `hook command environment changed` (`claude_settings`): a root `env` key that the diff adds, changes or removes is expanded, as `$K` or `${K` with the name ending where it cannot continue, by an active hook command of the same file on either side. A changed `env.CLAUDE_PROJECT_DIR` still gives the row, although Claude Code does not let it redirect the project-root forms.

None of the last three can fire on an unchanged tree, and none of the four changes a finding or the verdict. What stays silent is booked in R07 and R12: a body reached indirectly (an import, a build output not in the tree, a directory runner such as `run-parts`, an environment set outside the file, such as an `env` key in the other settings file or the host's own environment); a rewrite that changes only CRLF line endings, or only a file's executable bit, which the trees do not carry; a path the command does not spell as the repo-relative path at those boundaries (relative to a `cd` or `--directory`, `./`, `..` or `//` inside the path, a quote inside the path, globs, case variants); the module spellings `-mpkg.mod` and `-m "pkg.mod"`; and a gut behind a command that an earlier diff already respelled into an unresolved form (that earlier diff had its row).

## 4. Pin identity

A **pin** is a closed record:

```json
{
  "locator": "surface-specific string, stable across reformatting",
  "kind": "git_tag | git_sha | action_ref | digest_sha256",
  "value": "non-empty string",
  "product": "optional label, not used in identity"
}
```

`locator` examples: `gha_workflow:.github/workflows/tripwire.yml:uses:taipei49314/greenwash#0`, `declared_pins:greenwash`. In a workflow locator, `#<n>` counts, from 0, the earlier `uses:` lines in the same file that §3.1 records as pins of the same action (the value before its last `@`, with a non-empty ref after it; local `./` paths and `docker://` values are not pins), so a second step pinning one action is `#1`.

**Kind lattice** (stronger to weaker):

```
digest_sha256 > git_sha (full 40 hex) > git_tag (v-prefixed or annotated-looking) > action_ref-that-is-tag > action_ref-that-is-branch-or-floating
```

Classification of `action_ref` value `R`:

| `R` | Kind treated as |
|---|---|
| 40 lowercase hex | `git_sha` |
| matches `^v?[0-9]+\.[0-9].*` and contains no `/` | `git_tag` |
| `main`, `master`, `HEAD`, `latest`, empty, `*` | **floating** (weakest) |
| anything else (`feat/…`, unprefixed names) | **floating** |

**Unpin** (the `JUDGE_UNPINNED` event) is any of:

1. kind moved **down** the lattice;
2. value changed and the new value is floating;
3. pin **removed** while the locator’s consumer still exists (workflow still there, `uses` line gone or stubbed);
4. `digest_sha256` present at base, absent at head, other fields equal;
5. SHA shortened below 40 hex.

Pin **tightening** (tag → sha, sha + digest added) is not a finding.

Vendor directory **content** edits without a pin-record change are **not** `JUDGE_UNPINNED` in v0 (residual: silent patch of a vendored judge). tripwire’s “never patch the judge” is enforcement policy for that product; pinwash v0 only sees pin records.

`.pinwash/pins.json` is optional. Head-only creation of this file is not a finding. If it is present at base, every record must keep kind/value or a documented allow fingerprint (§10). Each base record is compared with the head record of the same `locator`; when the head file holds a locator more than once, its last record is compared (residual R04) (spec 15, AI-assisted ruling on #26 item 7). An unpin event above is `JUDGE_UNPINNED` at **high** (§6.3). A `digest_sha256` value is not read through the `action_ref` table: it is non-floating only as `sha256:` followed by 64 lowercase hex (surrounding whitespace ignored, as in that table), and any other digest value is floating and ranks as floating in the lattice, so a digest bump, or tightening to a well-formed digest, is no float, while a record relabelled `digest_sha256` that keeps a non-digest value has moved its kind down (`kind weakened`). Any other change of kind or value that is not tightening is `JUDGE_UNPINNED` at `warn` (`declared pin <locator> value changed`, the two values as `before` / `after`): pinwash cannot tell an upgrade from a downgrade or a repoint (`git_sha` a → b, `git_tag` `v1.0.0` → `v0.1.0`), so the change is reported and does not block at the default `fail_on`. Tightening is not a finding even when its new value names other content (`git_tag` `v1.4.0` → the `git_sha` of an older commit): residual R04.

**Skip flags are judged per command (spec 10).** A flag on a matcher or group object applies to every command under it. A flag is *added* when (1) a command present at base and head lost active (unflagged) occurrences and gained flagged ones; (2) fewer commands stay active and more are flagged overall; or (3) an active base command is absent at head while a command absent at base appears already flagged (rename plus skip). Commands are compared as multisets of their strings, so reordering is not a change. Adding a new flagged command next to unchanged ones is not a bypass of an existing hook, whichever flag it carries. "Command prefixed with a no-op" in §5 is a command shape, not a key: its v0 closed form is a shell comment (`#`).

An event whose command list is emptied is `HOOK_REMOVED` (§5), whatever its entries' `matcher` values; an entry emptied while a sibling entry keeps a command is `HOOK_REMOVED` under §5's "keeps no live command" disjunct (spec 27), else R12 (#10). This table has no matcher row (spec 13, #12 member 2, AI-assisted ruling: the row for `*` removed with the command list emptied could never fire, because `HOOK_REMOVED` covers that shape first).

**Pairing (spec 27, AI-assisted ruling on R12, #10).** Every §5 branch that compares a head command with a base command (a stub string, a `#` command, a stub body) pairs as multisets of command strings within the event, never by list position. A command whose string was in the event at base is compared with itself. A command the diff added (its string gained occurrences; each gained occurrence pairs once) is compared with the base command whose text a `#` carries, else with the first base command, in base order, that left the event (its string lost occurrences) and is not a `#` command or a stub string, and for the body form resolved at base to a non-stub body. Through spec 26 the stub-string branch paired by list index alone, and the comment-out and body-stub branches by list index first (spec 13): a reorder or an inserted placeholder fired at warn, and a judge removed while a stub-body, `true` or `#` sibling moved into its index blocked by accident of position, while the same removal with the sibling first passed. That removal is now §5's `HOOK_REMOVED` "keeps no live command", whatever the order.

Unknown JSON keys are ignored (not findings). A new unknown skip key is a residual (R06). A §5.1 flag key whose value is not the JSON boolean is read and not interpreted (R06); since spec 13 the file gets the `unknown_coverage` reason `hook skip flag value not boolean` (§7) when the diff adds or changes one, that is when an (event, command, key, value) occurrence is more frequent at head than at base, counted as a multiset as commands are: a hook object that carries such a value counts it once for each command the object holds itself or a hook item directly under it holds (on both hosts' shapes, every command the value applies to), or once with an empty command when it holds none; and also when a §5 hook finding fires in the file while either side holds one. The settings sources pinwash does not read decide the value in effect too (R02): a `--settings` file and managed settings outrank both repository files, user settings yield to them, `--setting-sources` can leave either repository file out, and a managed hook still runs under a repository `true` on Claude Code 2.1.296 (not on 2.1.42).

`matcher`, per-hook `if` and handler `type` changes with the command kept are residual R13 (#12): no finding, because which tools and events a selector governs is host semantics that pinwash does not evaluate. Since spec 13 they are reported in `unknown_coverage` with the reason `hook selector changed (not evaluated)`, once per file, when a command live on both sides of an event (no skip flag, not a §5.2 stub string, not commented out) differs in its entry's `matcher` value, its per-hook `if`, its handler `type` (absent reads as `command`; in the list form a `type` that names the hook's event is that event, not a handler type), or a `matcher` key below its entry. Commands pair by string first, and each string's selectors are judged on their own, so one command's narrowing cannot hide behind a sibling's widening of the same script; a command whose string changed is the same as one whose §3.3 targets are the same on each side. Values compare as parsed JSON, object key order ignored. A `matcher` change adds no row when the head matcher matches everything (absent, `""` and `*` are one value here, INFERRED from host docs), or when both values are names joined by `|` (each of ASCII letters, digits, `_` and `-`) and the head names include every base name: read as alternation, adding a name cannot narrow a selector. A per-hook `if` that is dropped only widens when the hook runs, so only a gained or changed `if` is a row. That reading of `|` is INFERRED host semantics (under exact-string matching, `Bash` → `Bash|PowerShell` would narrow). A command whose string and targets both change in the same edit is R12, and gets no row. The `cursor_hooks` row that §5.3 carried through spec 12 (`Write|Edit|Bash` narrowed away from `Bash`) is one of these changes: a row, not `HOOK_BYPASSED` (spec 13, AI-assisted ruling, #12).

### 5.2 Stub commands

A command string is a stub if, after trim, it matches **any** of (whole string, unquoted comparison):

- `true`
- `:` 
- `exit 0`
- `exit 0;`
- `echo {}`
- `echo "{}"`
- `python -c "print('{}')"`
- `python -c "print(\"{}\")"`
- `cmd /c exit 0`
- empty string

No regex beyond this closed list in v0. `python hooks/tripwire_stop.py --help` is **not** a stub.

A hook **body** file — a target resolved per §3.3 — is a stub if every non-blank, non-comment line (after strip) is a member of the closed set for its extension. Lines split at LF after CRLF→LF (§2); a lone CR also splits lines except in a `.sh` / `.bash` body, which the shell reads with a lone CR as an ordinary character (spec 13):

- `.py`: `pass`, `import sys`, `import os`, `if __name__ == "__main__":`, `sys.exit(0)`, `os._exit(0)`, `exit(0)`, `quit()`, `raise SystemExit`, `raise SystemExit(0)`, `print('{}')`, `print("{}")`
- `.sh` / `.bash`: `exit 0`, `true`, `:`
- `.js` / `.mjs` / `.cjs`: `process.exit(0)`, `process.exit(0);`
- `.ps1`: `exit 0`

An empty body after comment removal is a stub. A body containing any other line is not a stub — a real judge has work lines. No regex beyond these closed lists in v0.

**Block-capability shape (spec 7).** A body-stub list cannot enumerate reformattings that keep the file's function shape while removing its decision logic. A §3.3 target whose **base** body mentions `block` or `deny` (case-insensitive substring) is **block-capable**; if the **head** body mentions neither, and does not hold more of the closed exit-2 forms below than the base body does (spec 25), the gate can no longer refuse anything, and `GATE_STUBBED` fires (message "lost block capability") even though no closed line matches. The two shapes are independent — either can fire. A judge whose base body never mentions `block`/`deny` (e.g. refusal expressed only through exit codes) is invisible to this shape and stays residual. So do a gutted head body that keeps either word anywhere (a comment, docstring, string, identifier or unrelated word, or a dead branch that keeps the decision literal) and a `block` → `deny` swap: residual R07 (#11). The comparison is per target path, so a judge whose path changes has no base body to compare (R12, #10). Since spec 27 a body **can refuse** when it mentions `block` or `deny` in this sense or holds one of the exit-2 forms below, and on `cursor_hooks` also when it holds `followup_message`, the key Cursor reads from a `stop` hook's output (INFERRED from Cursor's hook documentation, as §6.1's Cursor events are); each marker is a case-insensitive substring read anywhere in the body, a comment or a dead branch included (R07). A Stop-like judge whose path changes is read by §5's retarget disjunct, which needs a **decision literal** in the base body: one of `"block"`, `'block'`, `\"block\"`, `"deny"`, `'deny'`, `\"deny\"` as a case-insensitive substring, or `followup_message` on `cursor_hooks`. Claude Code reads `{"decision": "block"}` (and exit status 2) from a Stop hook; the `deny` literals are kept for a script shared with `PreToolUse`, where it reads `"permissionDecision": "deny"`. The bare word is not enough there, because a hook that refuses nothing mentions it as easily as one that does (a transcript reader loops over content blocks); on a same path its disappearance is the evidence, across two paths it is not. A judge that refuses without a decision literal (an exit status), a copy that keeps either word anywhere (R07), and a retarget on another event stay R12.

**Exit-2 forms (spec 25, AI-assisted ruling on the spec 7 shape's exit-2 refactor false positive, #11).** Claude Code reads a hook's exit status 2 as a blocking error, as it reads `{"decision": "block"}` (executed on Claude Code 2.1.42 and 2.1.296: a Stop hook that exits 2 once makes the host run another turn, as one that prints the block decision does; one that exits 1 does not). The closed exit-2 forms are `exit 2`, `exit(2)`, `exitcode = 2` and `exitcode=2`, counted in the body casefolded after CRLF→LF: `exit 2`, `exitcode = 2` and `exitcode=2` where the character after them is not an ASCII digit, `>` or `<`, or the text ends (`exit 2` is not `exit 20`, nor the redirection `exit 2>/dev/null`, which exits with the last status, executed), and `exit(2)` wherever it occurs, since its `)` closes the argument (`process.exit(2)>0` refuses, executed), inside `sys.exit(2)`, `os._exit(2)`, `process.exit(2)`, `[Environment]::Exit(2)` and `SetShouldExit(2)` too. A head body that holds more of them than its base body keeps block capability: a judge refactored from the `block` decision to exit status 2 does not fire when the refactor raises the body's count of the closed forms. Such a judge also counts live for §6.1 again, so the file's other Stop findings are judged as without the false positive. Exit-2 forms the base already held do not count, so a gut that leaves boilerplate such as `cd … || exit 2` behind still fires. The forms do not make a base body block-capable: a judge that refuses only through exit status 2 stays residual (R07). A gutted head that gains an exit-2 form anywhere (a comment, a string, an unrelated `exit 2`) defeats the shape, as a kept `block` or `deny` does (R07, #11). A refactor to exit status 2 written outside the closed forms (`exit  2` with two spaces, `return 2` then `exit $?`, `exit $CODE`) still fires, as does one that does not raise the count (the refusal routed through an exit-2 helper or line the base already held, or usage exits merged while the decision moves to `exit 2`), one that moves the decision into another target of the same command, and the spec 7 shape's helper refactor (the decision moved into a file the body only calls).

For the last-Stop escalator (§6.1), a command at head is **live** unless it is a stub command string, carries a §5.1 skip flag (its own or one inherited from its matcher or group object), starts with `#` (§5.1), resolves (§3.3) only to stub bodies, **lost block capability**, or was **retargeted** to a body that cannot refuse (§5, spec 27). Nothing else is read: a command §3.3 does not resolve is live (§3.3 says when the run reports that) (spec 13, AI-assisted ruling, #10). §6.1 counts a live command the diff added to a Stop-like event only when it resolves to a target that can refuse (spec 27).

### 5.6 Job conditions (spec 22)

The `REQUIRED_CHECK_DROPPED` producer disjuncts (§5) read a single-line job `if:` (§3.1; a value continued on deeper lines is multiline and never read) in two closed ways (AI-assisted rulings R-13a and R-13b on #13, as the challenger amended them, and the review of 2026-10-10). GitHub wraps a condition with no status function as `success() && (…)`, and a job its condition skips reports Success to a required check, so the check passes on every pull request. Values are read, never evaluated. Both readings normalize alike: one optional layer of matching quotes is removed, with a single-quoted value's `''` decoded to `'` (YAML's one escape there) and a double-quoted value holding a backslash not read (the grammar does not decode its escapes); an unquoted value starting with `!`, `&`, `*`, `[` or `{` (a YAML tag, anchor, alias or flow node) is not read; the value must be exactly one `${{ … }}` with nothing outside it (text outside the braces makes GitHub build a string, which is truthy) or hold no `${{`; then whitespace outside single-quoted literals is removed, letters outside them are compared without case, and enclosing parentheses are stripped. A literal left open, or parentheses and brackets outside literals that do not balance, is not read (GitHub rejects such an expression). An operator inside parentheses or an index `[…]` is not top-level.

| Reading | Form |
|---|---|
| False | The spec 0–21 reading (`false` or `${{ false }}`, quotes stripped, in any letter case), an unquoted `false`, `False`, `FALSE` or `0`, or, unless the whole value is an unquoted YAML null (`null`, `Null`, `NULL` or `~`, an empty condition GitHub runs as `success()`), an expression that reads false: with a top-level `\|\|`, when every operand does; otherwise when one of its top-level `&&` operands, its enclosing parentheses stripped, is `false`, `0`, `null`, `!true`, `!always()`, `!!false`, `!!0`, `!!null`, or `!` before a parenthesized `true` or `always()` (GitHub's `&&` returns its falsy operand, so the whole condition is falsy whatever the others are). |
| Event filter | One or more top-level `\|\|` operands, each, its enclosing parentheses stripped, `github.event_name` or `github['event_name']` compared with `==` to a single-quoted event, in either order, without regard to case (letters outside literals and the index key compared without case; the event compared upper-cased, as GitHub compares strings with JavaScript's `toUpperCase`, so `ſ` is `S`), every event in {`schedule`, `workflow_dispatch`, `repository_dispatch`, `release`, `workflow_run`, `workflow_call`}: events whose runs never gate a pull request (spec 8 counts `push` and `pull_request` as the enforcement path). |

Anything else is not read (R14): a status function (`cancelled()`, `failure()`), a comparison, `null` compared, an event filter with `!=`, `&&`, `push` or `merge_group` alone, or a double-quoted string (not an expression GitHub accepts). The scan is linear and never recurses, so a value of any length or nesting reads the same on every interpreter.

## 6. Escalators

Applied in order, all deterministic. No scores.

1. If `HOOK_REMOVED` or `HOOK_BYPASSED` or `GATE_STUBBED` removes or stubs the **last remaining** Stop-like hook, severity becomes **critical**. The last one is gone when no Stop-like event in that file keeps a command that is live under §5.2 and either was in that event at base or resolves (§3.3) to a target that can refuse (§5.2); the count is per file. A command was in the event at base when its string was, or when it resolves at head to a target set that a command of the event not beginning with `#` resolved to at base (a respelling, such as `python` → `python3`; a planted `#` line uncommented is a command the diff added). Since spec 27 (AI-assisted ruling on R12, #10) a hook the diff adds keeps no Stop judge "remaining" unless pinwash read a body of it that can refuse (§1.7: what the agent wrote in the same diff is no evidence that a harness still runs); through spec 26 an added `echo ok`, unresolved command or resolved script kept a gutted, stubbed, commented-out or skip-flagged last judge at `warn`. A sibling that keeps `block` or `deny`, a §5.2 exit-2 form (boilerplate such as `cd … || exit 2` included) or, on `cursor_hooks`, `followup_message` (in any case), anywhere (a comment, a string, a dead branch) still counts (R07), and so do one that a verb names without running it (R11) and one an earlier diff added (R12). Stop-like events are a closed, case-sensitive set per surface (spec 13, #26 item 6, AI-assisted ruling): `Stop` on `claude_settings`; `stop` on `cursor_hooks`, the Cursor event that runs when the agent loop ends and can submit a follow-up message. `afterAgentResponse` and `afterAgentThought` only observe a turn, `subagentStop` belongs to a subagent (as Claude's `SubagentStop` does, which is not Stop-like either), and `finish` and `Stop` name no Cursor event; a hook under any of these names, or any other, never keeps this escalator off, so moving the last Stop-like judge to one of them is removing it. Which Cursor events run, and what they can return, is taken from Cursor's hook documentation, not observed on a host. The settings-root `disableAllHooks` finding (§5.1, spec 24) switches off every Stop-like command of both settings files at once; it is critical when either file kept a live Stop-like command at base, and no other finding's count reads the switch.
2. If `REQUIRED_CHECK_DROPPED` removes the last remaining required context in a ruleset file, severity becomes **critical**.
3. `JUDGE_UNPINNED` (spec 15, AI-assisted ruling on #26 item 1). On a workflow pin (`action_pin`), severity becomes **high** when the event moves a non-floating pin (`git_sha` or `git_tag` by the §4 table) to floating (unpin 1, 2 or 5), and **critical** when the head workflow file then keeps no non-floating pin. A non-floating pin removed while its workflow remains (unpin 3) is **critical** when the head workflow file then keeps no non-floating pin, and otherwise stays `warn` (R15). Every other workflow unpin event stays `warn`: a kind drop that does not float (`git_sha` → `git_tag`), a floating value changed to another floating value (`@v3` → `@v4`, `@v1` → `@main`), and a floating ref removed, since a ref that was already floating had no pin to weaken. On `declared_pins`, every unpin event is **high**: a record removed (the file deleted included), `digest_sha256` lost, kind moved down, or value floating. The asymmetry is deliberate: the declared file is an opt-in list of judge identities, while a workflow pins every action it uses and the movable tag of a third-party action belongs to that action's upstream, so a drop that stays `warn` among a workflow's actions blocks on a declared judge.
4. `SURFACE_UNPARSEABLE` at head when base parsed: **high**.
5. Otherwise leave the rule's base severity — `warn`, except the producer-side `REQUIRED_CHECK_DROPPED` disjuncts, which base at `high` (spec 9), and the §10 exemption-channel severities (`CONFIG_RELAXED` at `.pinwash/allow.toml` is `critical`; `EXEMPTION_ADDED` is `critical` when an added record's `created` is after today, spec 11).

Default `fail_on` is **high**. `warn` findings do not fail the run. `critical` and `high` do. This matches checkwash’s “visible warn can still pass” so installing pinwash on a noisy docs edit of SKILL.md does not by itself brick merge until phrases hit and escalate — `SKILL_BYPASS` stays warn unless later spec says otherwise. v0: `SKILL_BYPASS` never escalates (phrase hits are review, not merge-block). `PERMISSION_WIDENED` escalates to **high**. `CONFIG_RELAXED` escalates to **high**; at `.pinwash/allow.toml` it is **critical** (§10). `EXEMPTION_ADDED` stays `warn`, except an addition whose `created` is after today, which is **critical** (§10, spec 11). Spec 9: a required check that can no longer run on any enforcement path is a dropped check, so its producer-side shapes block at the default `fail_on` (round 3 live warn-gap specimen: `# on: push` fired warn and the verdict stayed pass). That sentence gives the reason for the producer-side severity; it is not a trigger (spec 14, AI-assisted ruling on #13): this section raises findings §5 produced, and a trigger written as an effect would be an open rule inside §5's closed table. Other shapes after which a linked producer no longer runs are R14; §5.5 reports them as `unknown_coverage` until a bump adds a closed form of them to §5.

## 8. Exit codes

| exit | meaning |
|---|---|
| 0 | no finding at or above `fail_on`; engine finished |
| 1 | verdict `block` |
| 2 | engine error, including unexpected exceptions and unreadable git trees |

A crash must not exit 1. Parse failures of **subject** surfaces are findings (`SURFACE_UNPARSEABLE`), not exit 2, unless git itself cannot be read.

## 9. Determinism

- No floats in the verdict path.
- No network.
- No clock in findings JSON.
- CRLF→LF; JSON bytes identical on Windows / macOS / Linux for the same trees and Python 3.11–3.13 (grammar of JSON/TOML bounded subset, not of subject Python).
- No random.
- Zero runtime dependencies.

## 10. Exemptions

Base-side `.pinwash/allow.toml` only, per fingerprint, never per-rule-glob:

```toml
[[allow]]
fingerprint = "HOOK_REMOVED/.claude/settings.json/v1:…"
rule = "HOOK_REMOVED"
reason = "…"
author = "…"
created = "2026-09-27"
expires = "2026-12-24"
```

All six keys are required and non-empty; `created` and `expires` must parse with Python 3.11+ `date.fromisoformat` (ISO 8601 dates in extended, basic, or week form; not ordinal). "Today" is `PINWASH_TODAY` if set, else the current local date of the host running pinwash — the only clock that may affect a verdict, overridable for replay.

A record is **valid** when `expires` is at most 180 days after `created` and not before today (the expiry day itself counts; an `expires` before `created` passes the first condition). An **exemption** is a valid record. Records that fail validity are invisible to both checks below: deleting or editing one is not a finding, and adding one emits nothing.

A base exemption is **in force**, and drops the finding whose `fingerprint` and `rule` it names, only while `expires` is also at most 180 days after the earlier of `created` and today (spec 11). A `created` date in the future therefore cannot lengthen the window: no record is in force more than 180 days before it expires. Validity alone decides the checks below, so a future-dated record is visible when it is added and when it is edited or deleted, even on days it is not yet in force. A record is also not in force while another valid base record for the same `fingerprint` and `rule` has its `created` after today (spec 11). Records added in one change whose windows follow one another would otherwise keep one fingerprint exempt for more than 180 days after that change; that needs a record whose `created` is after the day it is added, and adding one blocks (below), while such records already in a base shrink to their last one. Renewing an exemption later with a fresh record is an ordinary addition (warn).

Head-side **append-only** valid additions emit `EXEMPTION_ADDED` at warn (visibility), or at **critical** when any added record's `created` is after today (spec 11). Editing or deleting a base exemption is `CONFIG_RELAXED` at critical; an edit is any change to a base exemption record, not only its removal. A head `allow.toml` that is missing or not UTF-8 cannot confirm any base exemption, so it counts as deleting all of them. A warn addition is in force on every later run whose base holds it, merged or only committed at the `HEAD` that `check` compares the worktree against: that pre-seed is residual R18 (#17).

The exemption channel never exempts its own findings (spec 11): `CONFIG_RELAXED` and `EXEMPTION_ADDED` at `.pinwash/allow.toml` are always reported. A record naming either one is still a valid record, so adding, editing, or deleting it is visible as above, but it drops nothing. `CONFIG_RELAXED` from `checkwash_config` (§5) is a different channel and stays exemptible.

## 13. Default CLI (when implemented)

```
pinwash check [RANGE]
pinwash check              # worktree vs HEAD, i.e. HEAD..WORKTREE (§2)
pinwash --version
pinwash doctor             # own tests / spec hash; does not judge the subject
```

`doctor` passing is not a subject pass.

`check` with no range reads configuration, allowlists and every other base-side input from `HEAD`, which a session that commits can move. `BASE..WORKTREE` (§2, spec 16) reads them from a base recorded before the session. How a consumer combines ranges to judge an agent session, and what it counts as a pass, is consumer policy (README), like a gate on `unknown_coverage` (§7).

## 14. Claims policy

- Do not say pinwash “secures agents” or “stops jailbreaks”.
- Do not say a repo “has an intact harness” because pinwash exited 0.
- Do not treat pinwash as tripwire, or tripwire as pinwash.
- Quote run labels, spec version, and pinwash revision with every measurement.

- Parsing Python/JS hook bodies (R07).

- Live GitHub / Cursor API reads.
- Replacing checkwash CI/test rules.
- Auto-fixing the diff.
